2. Implementation of Multi-Factor in authentication.

Authentication is a process by which a system verifies the identity of a user or entity. It proposes a formula that combines different factors to ensure the authenticity of the user. The formula can be summarized as follows:
**Authentication = (What you know) + (What you have) + (What you are) + (Where you are) + (What you do)**
Within that formula, each component represents a different factor that contributes to the overall authentication process. Combining multiple factors (multi-factor authentication) enhances security by requiring users to provide more than one form of verification.
Defined in NIST Special Publication 800-63B, the Level of Assurance (AAL) is a framework that categorizes authentication methods based on their security strength. The AAL levels range from AAL1 (lowest assurance) to AAL3 (highest assurance), with each level requiring different combinations of factors for authentication. As such, organizations can choose the appropriate authentication methods based on their security requirements and risk tolerance. And that is the methodology on choosing examples: based on the linear development of the authentication methods of an organization, from the simplest to the most complex, and from the least secure to the most secure.

2.0. Memorized Secrets (AAL1)

This is the most common and simplest method of authentication, which requires users to provide a username and password combination. While being widely used, this method has limitations in terms of security, as passwords can be easily compromised through various means such as phishing attacks or brute force attacks. According to NIST, this method is classified as AAL1 (Authentication Assurance Level 1) since it relies solely on something the user knows. 

2.1. Memorized Secrets + OTP (AAL2) x

To enhance the security of the basic authenticate implementation, organizations combine memorized secrets with One-Time Passwords (OTPs) or Time-Based One-Time Passwords (TOTPs), which introduces a very basic implementation of multi-factor authentication. A part from the username and password (something the user knows), users are required to provide a time-sensitive OTP (something the user has), which is typically generated by an authenticator app or sent via SMS. This combination elevates the authentication process to AAL2, providing a higher level of assurance.

As a student, who is a part of an organization (e.g., a university), I can login to Microsoft 365 using my university email and password, and then I can choose to receive a TOTP generated by the Microsoft Authenticator app on my mobile device. Under the hood, Microsoft Entra ID handles the authentication process, verifying both the password and the TOTP before granting access to the requested resources. This implementation demonstrates how organizations can leverage multi-factor authentication to enhance security while providing a seamless user experience.

2.2. Multi-Factor Cryptographic Software (AAL2) x

This method integrates software-based asymmetric private keys stored within an operating system's filesystem, keychain, or Trusted Execution Environment (TEE). As user authenticating to the service, the system mandates a local challenge that require the user to provide a password (something they know) or a biometric factor (something they are) to unlock the private key. The system then uses the private key to sign a challenge, which is sent to the service for verification. This method can achieve AAL2, as it requires both knowledge and possession factors for authentication.  

For instance, when I login to my Google account on a Windows 11 device, Google Identify handles the authentication process while WebAuthn API manages the local challenge (a cryptographic challenge generated by the browser). As the challenge is passed down to my local system, Windows Hello prompts me to provide my password/PIN (something I know) or a biometric factor (something I am) to unlock the private key which is sent to Google for verification. The key is safely stored locally or embedded in a Trusted Platform Module (TPM) chip, ensuring that it cannot be easily extracted or compromised.

2.3. Multi-Factor Cryptographic Device (AAL2 or AAL3)

This system is one of the most secure methods of authentication, which involves the use of cryptographic devices such as smart cards or USB tokens. Users are required to provide their memorized secrets (something they know) along with the physical device (something they have). Depending on the implementation and security measures, this method can achieve AAL2 or AAL3, offering a robust authentication mechanism. The use of cryptographic devices adds an additional layer of security, making it more difficult for attackers to compromise user accounts.

Google provides an example of this method through its Titan Security Key, which is a USB device that supports FIDO2 and U2F protocols. When I log in to my Google account, I am prompted to insert the Titan Security Key into my computer's USB port. The key generates a unique cryptographic signature that is sent to Google's servers for verification. This approach ensures a very high level of security, as the physical device is required for authentication, making it significantly harder for attackers to gain unauthorized access.

2.4. Federation and Assertions (depends on the security level of the assertion, it can be AAL1, AAL2, or AAL3)

Federation and assertions method is now widely used a long side with OTPs or TOTPs as the main and only authentication in modern applications. This method allows users to log in using their credentials from a trusted third-party identity provider, such as Google or Microsoft. The security level of the assertion can vary based on the measures implemented by the identity provider, and it can achieve AAL1, AAL2, or AAL3. This approach is particularly useful for businesses that want to leverage existing identity providers for authentication, reducing the need for users to remember multiple credentials while still maintaining a high level of security.

An example of this implementation includes using OpenID Connect (OIDC) / OAuth 2.0 and Microsoft Entra ID for federated authentication. When I log in to a university platform that relies on Microsoft Entra ID as its Identity Provider (e.g., Brightspace), I am redirected to the Microsoft Entra ID login portal. Here, I enter my institutional credentials and complete a Multi-Factor Authentication (MFA) challenge, such as a TOTP or a push notification, managed by Entra ID. Upon successful verification, Entra ID generates a secure cryptographic token (assertion) and redirects it back to Brightspace. Brightspace validates this token to grant access to the requested academic resources. This model can be very secure, or none at all, depending on the security level of the assertion and the MFA methods enforced by the identity provider.
